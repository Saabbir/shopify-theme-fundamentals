**TL;DR:** The three objects that connect a merchant's schema choices back to the Liquid that renders them.

## settings

`settings` holds every value from the theme's global `settings_schema.json`, read the same way from anywhere in the theme:

```liquid
{{ settings.heading_font }}
{{ settings.show_vendor }}
{{ settings.color_scheme }}
```

Every property under `settings` corresponds exactly to an `id` in `settings_schema.json` — there's no separate reference needed beyond knowing the schema itself, since `settings` is just that schema's current values, always in sync with whatever a merchant last saved in the theme editor. [28. All About Theme Settings](/all-about-theme-settings/) covers exactly where this data lives on disk and how it differs from a section or block's own settings.

## section

`section` represents the specific section instance currently rendering — its own settings, its blocks, and a few properties about where it sits on the page.

```liquid
{{ section.id }}
{{ section.settings }}
{{ section.blocks }}
{{ section.index }}
{{ section.index0 }}
{{ section.location }}
```

`section.settings` works exactly like `settings`, just scoped to this one section's own schema rather than the theme-wide one. `section.blocks` is the array of `block` objects to loop over — the standard way any section with blocks renders its content:

```liquid
{% for block in section.blocks %}
  {{ block.settings.heading }}
{% endfor %}
```

`section.location` tells you *where* a section is rendering from — `template` for a section placed directly in a JSON template, a section group's own type (`header`, `footer`, `custom.<type>`) for one rendered inside a section group, `static` for a [statically rendered section](/all-about-sections/section-fundamentals/), or `content_for_index` for the legacy syntax it replaced. `section.index`/`section.index0` give a section's 1-based or 0-based position within that same location — useful for something like deciding whether a section is "below the fold" for lazy-loading purposes, but **not** reliable for anything display-related, since it returns `nil` for a statically rendered section, inside the theme editor, and when a section is re-rendered through the [Section Rendering API](https://shopify.dev/docs/api/section-rendering).

:::caution[section.index is for performance decisions, not display logic]
Because `section.index` can be `nil` in several common contexts (the theme editor being the big one — meaning it's `nil` every single time a merchant is actively editing), building a feature that depends on it rendering correctly in the editor will quietly misbehave for the one audience that's looking right at it. Reserve it for behind-the-scenes choices like `loading="lazy"` thresholds, never for anything a merchant needs to see working while editing.
:::

## block

`block` represents one block within a section (or, inside a theme block file itself, the block being rendered) — its own settings plus a couple of properties the theme editor depends on.

```liquid
{{ block.id }}
{{ block.type }}
{{ block.settings }}
{{ block.shopify_attributes }}
```

`block.type` is the free-form string defined in that block's own schema entry — the usual way a section's loop decides which markup to render per block type:

```liquid
{% for block in section.blocks %}
  {% case block.type %}
    {% when 'heading' %}
      <h2>{{ block.settings.text }}</h2>
    {% when 'image' %}
      {{ block.settings.image | image_url: width: 800 | image_tag }}
  {% endcase %}
{% endfor %}
```

`block.id` is dynamically generated by Shopify and can change — never hardcode a comparison against a specific block's ID, and never rely on it as a stable key across page loads. `block.shopify_attributes` is a ready-made string of `data-*` attributes the theme editor's own JavaScript uses to identify which DOM element corresponds to which block, enabling in-editor selection highlighting and drag-to-reorder — it only returns a real value inside the theme editor, and should be spread onto each block's outermost rendered element exactly as-is:

```liquid
<div {{ block.shopify_attributes }}>
  {{ block.settings.text }}
</div>
```

:::note[Why shopify_attributes has to go on every block's own element]
Skipping `block.shopify_attributes` doesn't break anything for a shopper on the live storefront — it only breaks the theme editor's ability to let a merchant click directly on a block to select and edit it, select it from the sidebar and see it highlighted, or drag it to reorder. The attribute costs nothing outside the editor, so it's standard practice to always include it rather than deciding per-block whether the editor experience matters.
:::

## Key takeaways

- `settings` mirrors `settings_schema.json` exactly; `section.settings`/`block.settings` work identically but are scoped to that section's or block's own schema.
- `section.index` is `nil` in the theme editor, in a statically rendered section, and through the Section Rendering API — safe for a performance threshold, unsafe for anything display-related.
- `block.id` is dynamically generated and can change; never build logic that depends on a specific block's ID staying the same.
- `block.shopify_attributes`, spread onto a block's outermost element, is what makes a block selectable, highlightable, and draggable inside the theme editor — it's inert outside the editor, so there's no real reason to ever skip it.
